# TZY-353 Research: image dimensions in the post form

**Question:** Should the two `<img>` elements in `src/Presentation/Views/admin/posts/form.php` receive HTML `width` and `height` attributes, and does the rendered layout reserve space while their image data loads?

**Research date:** 2026-11-09

## Findings

- The HTML Standard maps an `<img>` element's `width` and `height` attributes to dimension properties and to its preferred aspect ratio. The values should describe the image's intended dimensions/aspect ratio; they can help the browser determine layout before image data has loaded. Source: [HTML Standard — dimension attributes](https://html.spec.whatwg.org/multipage/images.html#dimension-attributes).
- MDN explains that image aspect ratios can prevent loading jank by reserving media space before paint. It also describes responsive sizing and the role of CSS `aspect-ratio`. Source: [MDN — Images, media, and form elements](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Styling_basics/Images_media_forms) (consulted 2026-11-09).
- The featured preview's `src` is the post's arbitrary saved URL or a URL entered by the user, and JavaScript can replace it at runtime. There is no single intrinsic size available to the static template. CSS currently gives `.wp-featured-preview img` `width: 100%` and `aspect-ratio: 16 / 9` (with a `190px` max height and `object-fit: cover`), defining a stable preview slot independently of the source file's intrinsic dimensions.
- The media picker is rendered from `MediaFile` records. A record may carry source dimensions (the regression fixture is 640×480), but thumbnails are cropped into a fixed-height 55px slot using `width: 100%`, `height: 55px`, and `object-fit: cover`. The source ratio is not the display ratio, so copying source dimensions into attributes would not describe the displayed crop's layout. The CSS-defined box already has a width from its grid column and a fixed height.
- The repository's regression checks render the empty and populated post form and verify that the CSS reserves both preview and thumbnail slots without guessing dimensions. This is the appropriate behavior for the dynamic sources and crop layout. The code change will make those assertions explicitly cover both image tags as a single regression.

## Decision and feature impact

Do not add guessed numeric HTML dimensions to either tag. Keep CSS sizing as the layout contract: the featured image uses a 16:9 preview slot and media thumbnails use a fixed-height crop slot. Strengthen the focused regression to ensure rendered markup remains dimension-agnostic while both CSS reservations remain present. This avoids distorting or misrepresenting dynamically sourced images and covers the detector's static-template limitation.

## Research limitations

The URLs are arbitrary and may point to external assets, so their bytes and intrinsic dimensions cannot be reliably known at template-render time. No browser session or Core Web Vitals measurement was performed; the source check and existing CSS establish the reserved geometry, but do not claim a measured layout shift or CWV impact.
