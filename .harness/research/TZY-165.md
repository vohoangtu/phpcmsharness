# TZY-165 Research Report

- **Date:** 2026-11-08
- **Question:** With no backlog item or topic specified, which safe, high-value CMS improvement should AutoTopic select after inspecting the repository?

## Repository-based ideas considered

1. **Add CSRF protection to state-changing forms and routes.** `public/index.php` starts a PHP session and registers many POST routes, while the admin and storefront templates contain POST forms and the request router currently owns route dispatch. A shared token mechanism could protect these actions consistently without adding persistence or weakening the Domain boundary.
2. **Prevent duplicate or colliding Harness task codes.** `TuzygentHarnessService::createTask()` derives the next code from `count(findAll()) + 1`; deleting a task can therefore cause a reused code, and concurrent task creation can race. A sequence/unique constraint through the repository port and SQLite adapter would make task identity more reliable.
3. **Add pagination to growing admin lists.** Product, post, order, comment, user, and Harness pages load lists into memory and render them in one response. Pagination would improve response time and usability as content grows, but spans several repository ports, adapters, services, and views.

## Selection criteria and decision

The ideas were compared by user/security impact, implementation scope, fit with the existing architecture, and regression risk. **CSRF protection** is selected: it closes a security gap affecting many existing browser actions, can be centralized at the Presentation HTTP boundary, and can use the session already started by the front controller. The design should use a cryptographically random synchronizer token stored in the session, submit it in a hidden field for HTML forms, and reject missing or invalid tokens on state-changing requests. The token stays out of URLs and Domain code. All POST forms—including login and storefront forms—must be covered for a consistent policy.

The task-code sequence and list pagination ideas remain candidates for later work.

## External research

OWASP's Cross-Site Request Forgery Prevention Cheat Sheet recommends the synchronizer-token pattern for stateful software. It says the server should generate an unpredictable secret token, transmit it in a form field or request payload, compare the submitted value with the session value, and reject absent or invalid tokens. It also advises against putting the token in a URL. This supports a session-backed token integrated at the router and hidden fields in forms; one token per session avoids invalidating other open tabs.

- Source: [OWASP Cross-Site Request Forgery Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
- Accessed: 2026-11-08
- Feature effect: use `random_bytes()` for token creation, `hash_equals()` for constant-time comparison, and fail closed on missing/invalid POST tokens.

## Scope and limitations

The implementation will cover browser POST routes and their HTML forms, including the login form and AJAX-triggered Harness tick form. The research used the authoritative OWASP guidance above; no additional external references were needed. The report records repository observations and planned design before implementation changes.
