# TZY-339 research: product description HTML rendering

**Question.** Is `$product->description` unsafe when rendered in `frontend/shop/show.php`, and how should the storefront preserve editor formatting while handling hostile markup?

**Findings (researched 2026-11-09).**

- The value is accepted by the admin product form (`ProductController::save()` passes submitted data to `ProductService::saveProduct()`), stored as product description, and later loaded into the `Product` entity. It is therefore persisted editorial content, not inherently plain text. The storefront inserts it in an HTML element body, where rich formatting is an intentional feature.
- The current view calls the shared `HtmlContentSanitizer::sanitize()` at the insertion point. That helper uses the project dependency HTML Purifier, with an explicit allowlist for common editorial tags and only `http`, `https`, and `mailto` URI schemes. The exact view already has regressions checking preserved paragraphs/headings/formatting/links and removal of scripts, event handlers, images, SVG, iframe, styles, and unsafe or obfuscated URI payloads. This means the static AutoTopic observation alone does not establish an exploitable flaw.
- HTML Purifier's official configuration reference describes `HTML.Allowed` as a tag/attribute allowlist and `URI.AllowedSchemes` as the allowed URI scheme whitelist. Those controls match the rendering need better than escaping the whole description, which would destroy the required rich formatting.
- PHP's `htmlspecialchars()` is appropriate when a value is plain text destined for HTML text/attribute context, but would render this editor-authored HTML literally. It is already used for the short description, which is plain text. It is not a substitute for a rich-HTML sanitizer.
- The installed dependency is `ezyang/htmlpurifier` v4.19.1 per `composer.lock` (release timestamp recorded there: 2026-09-15); no dependency replacement is needed.

**Decision / impact.** Keep rich description content as editorial HTML and sanitize at the HTML-body output boundary with the maintained, already installed HTML Purifier integration. Preserve the existing restrictive allowlist and URI scheme policy. Add only focused regression coverage if verification reveals a gap; do not change the view to blanket escaping or treat the heuristic signal as proof of vulnerability.
