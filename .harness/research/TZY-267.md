# TZY-267 Research & Selection Report

## Repository review

The repository has a `Subscriber` entity, outbound port, SQLite adapter, and application service, but none are registered in `Container`, used by a controller, or exposed through a public route. The generated subscriber schema stores `name` and `code`, so it is not yet suitable for storing an email address. The frontend layout already renders flash messages, and every non-GET route is protected by the router's session CSRF token check. Existing public forms use POST/redirect/GET.

## Brainstormed ideas

| Idea | Value | Fit and risk |
| --- | --- | --- |
| Complete a public newsletter signup flow backed by the existing subscriber module. | High: gives visitors a direct way to subscribe and makes an otherwise unreachable CMS feature useful. | Fits the existing frontend, flash, CSRF, service, port, and SQLite patterns. Requires an additive persistence migration and duplicate handling; scope can remain limited to subscribing. |
| Publish an FAQ page using the existing FAQ entity and repository. | Medium: gives visitors self-service answers. | The existing FAQ fields are generic `name` and `code`, not question and answer; a useful feature would require a larger model redesign and admin authoring surface. |
| Add a public wishlist page using the existing wishlist module. | Medium: helps shoppers revisit saved products. | The current wishlist support is session-oriented and would need a new user/session-facing flow, route, and integration with cart behavior; broader than the missing subscriber flow. |

## Selection criteria and decision

I compared user value, direct evidence in the current repository, fit with existing conventions, implementation scope, migration risk, and whether the behavior can be covered with focused regression checks. The newsletter flow has the clearest unused foundation and can be completed without adding a third-party dependency or changing unrelated modules. I selected a public, CSRF-protected signup that validates and normalizes an email address, persists it through the Subscriber outbound port and SQLite adapter, and gives the visitor a clear success or validation message. The persistence change will preserve existing subscriber records and legacy fields.

## Research question

Which protections and validation behavior should a small server-rendered public newsletter signup use in this PHP CMS?

## Findings and implementation impact

- OWASP recommends the synchronizer token pattern for stateful software: generate an unpredictable server-side token, submit it with the form, and validate it on every state-changing request. The CMS already implements this pattern at the router, so the signup form will include the existing CSRF field and use POST; no bespoke bypass or token mechanism is needed.
- The PHP manual documents `FILTER_VALIDATE_EMAIL` as an email validation filter and notes that validation does not confirm that an address exists. The signup service will reject syntactically invalid addresses, normalize surrounding whitespace and case for duplicate matching, and avoid claiming that an address has been verified. Email ownership verification and outbound mail are outside the current repository's capabilities.

## Scope and limitations

This feature records a subscription request only. It does not send mail, verify address ownership, implement unsubscribe links, or claim consent beyond the explicit signup action. External sources were accessible. PHP's syntax filter is not a deliverability or mailbox-existence check.
