# TZY-266 Research & Selection Report

## Repository review

`CmsTopicGenerator` is the source-based discovery path used by `TuzygentHarnessService::discoverNextEvolutionTask()` when the backlog is empty. It already scans PHP, templates, JavaScript and CSS for security, accessibility, architecture and test-coverage signals; generated items are deliberately review candidates, ranked by P0/P1/P2, capped at ten, and suppressed while the same target is active. Existing tests use temporary repositories to verify findings, stable identities, deduplication and false-positive boundaries. `AuthService::attemptLogin()` currently calls the outbound `regenerateId()` port before storing an authenticated principal, but no AutoTopic rule guards that security invariant against future regressions.

## Brainstormed ideas

| Idea | Value | Fit and risk |
| --- | --- | --- |
| Add a source-level AutoTopic check that authentication code rotates the session ID before storing an authenticated principal. | High: flags a session-fixation regression at the point where login elevates privileges. | Fits the existing conservative, evidence-based detector style. Can be bounded to the authentication application service and report only a review candidate; low implementation risk. |
| Add a general scanner for stale internal links after route changes. | Medium: helps keep navigation and route declarations aligned. | The generator already has `findInternalLinksWithoutRoutes()`, so this overlaps existing coverage and would add little value. |
| Add a detector for application services missing focused tests. | Medium: improves maintainability and regression coverage. | `findUntestedServices()` already provides this signal; extending it would need a separate, demonstrable gap to avoid duplication. |

## Selection criteria and decision

I compared security impact, evidence available in the current code, overlap with existing detectors, compatibility with the current architecture, and the ability to test the behavior without changing runtime authentication. The session-ID rotation invariant has the strongest security value, is directly evidenced by the existing `AuthService` port call, is not covered by current AutoTopic checks, and can be implemented as a static review signal without touching authentication behavior. I selected this idea.

## Research question

What source-level invariant should the CMS preserve when authentication changes an anonymous session into an authenticated session, and what constraints should guide a session-ID rotation review?

## Findings and implementation impact

- OWASP's Session Management Cheat Sheet states that session-ID regeneration is mandatory when authentication changes the privilege level, to mitigate session fixation. This supports a P0 review candidate when an authentication flow stores a principal but has no preceding session-ID regeneration signal. The detector will explicitly describe itself as heuristic and request verification of the actual call path rather than claim exploitability.
- PHP's `session_regenerate_id()` manual documents that the function replaces the current ID while retaining session data, returns success/failure, and warns that immediately deleting the old session can create races on unstable networks. This supports checking for the rotation call without prescribing the deletion option; the detector must not recommend blindly passing `true`.

## Scope and limitations

The feature will be a source-level AutoTopic finding, not a runtime authentication change. Static inspection cannot prove a principal assignment is reachable, whether a helper rotates the session ID indirectly, or whether infrastructure manages sessions differently. External sources were accessible; the conclusions above are tied to the cited OWASP and PHP documentation.
