# TZY-299 — Rich HTML rendering in product details

**Research date:** 2026-11-08

## Question

What is the correct treatment for `Product::$description` when the product detail template renders it in an HTML body, and how can the application preserve editor-authored formatting without allowing active content?

## Findings

1. The storefront description is not plain text. The admin product form exposes a visual editor and source mode, and its field is saved by `ProductService` as raw HTML. The consumer is an HTML element body in `frontend/shop/show.php`. Escaping with `htmlspecialchars()` would safely display the markup as text but would break the supported rich content behavior.
2. OWASP's XSS Prevention Cheat Sheet says output protection must match the destination context. For user-authored HTML, output encoding breaks intended formatting, so a maintained HTML sanitizer is the appropriate defense. It also warns to keep the sanitizer patched and not to mutate sanitized output afterward.
3. PHP's `htmlspecialchars()` manual confirms that it encodes HTML-special characters for text contexts and supports explicit quote, invalid-sequence, and encoding flags. That is appropriate for the separate plain-text product fields, but not for the rich HTML description.
4. This repository already requires `ezyang/htmlpurifier` (`^4.18`) and routes both the admin editor preview and storefront description through `App\Presentation\Security\HtmlContentSanitizer`. Its `HTML.Allowed` policy retains common text formatting, headings, lists, blockquotes, and links; `URI.AllowedSchemes` permits only HTTP, HTTPS, and mailto. The product description is therefore editorial HTML, but static dataflow alone does not establish a vulnerability; regression tests should demonstrate both retained formatting and removal of active payloads.

## Effect on implementation

Keep the description as rich HTML, sanitize at the rendering boundary using the existing shared HTMLPurifier policy, and test the storefront output with safe editorial markup and hostile markup including script/event handlers, unsafe URI schemes, and embedded active content. Do not report a confirmed vulnerability unless those tests show unsafe content survives.
