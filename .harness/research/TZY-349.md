# Research report: TZY-349 — Dynamic rich HTML rendering in the product view

**Research date:** 2026-11-09

## Question

The product detail view renders `$product->description` as HTML. Is this plain text that should be escaped, or editor-authored rich HTML that needs a maintained sanitizer? What checks should protect the rendered content without removing legitimate formatting?

## Findings and impact

1. **The output defense must match the intended content.** OWASP distinguishes ordinary text output, which should be encoded for its context, from user-authored HTML that must retain markup. When rich HTML is a product requirement, OWASP recommends a maintained HTML sanitizer and warns that modifying sanitized output can undermine the protection. This supports keeping the product description as rich text and sanitizing it at the HTML body sink instead of escaping all tags or trying to strip a few known-dangerous strings.
2. **The source accepts editor-authored markup.** In this repository, the admin product form labels the field “Mô tả chi tiết sản phẩm” and submits it through a rich-content editor; `ProductService` stores the description string, and the SQLite adapter retrieves it as a string. Product create/edit/save routes require admin authentication. The form escapes the raw source textarea and sanitizes the visual editor preview. The storefront view therefore handles persisted editor content, not a value guaranteed to be plain text, and is the final relevant output boundary.
3. **Use an explicit, narrow allowlist and exercise active-content payloads.** HTML Purifier documents `HTML.Allowed` as the setting for limiting allowed elements and attributes. The current shared sanitizer permits common editorial tags, selected link attributes and only `http`, `https`, and `mailto` URI schemes. Regression coverage should confirm that headings, emphasis, lists, blockquotes, and safe links survive, while scripts, event attributes, embedded active content, and unsafe or obfuscated URI schemes do not.
4. **When content is plain text, use HTML escaping with a declared encoding.** PHP documents `htmlspecialchars()` for encoding characters with HTML significance, and `ENT_QUOTES | ENT_SUBSTITUTE` with UTF-8 is appropriate for untrusted strings in HTML text/attribute contexts. Applying that to the rich description itself would display markup literally and break the editor contract; the short description elsewhere is correctly treated as text and escaped.

## Repository decision

Retain rich editorial formatting and sanitize at the storefront output boundary using the existing maintained HTML Purifier dependency. Verify the actual product-view rendering path and adversarial payload behavior with regression assertions; do not infer a vulnerability merely from a raw-HTML detector signal.
